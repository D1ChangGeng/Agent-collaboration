# 05｜P2 非阻塞产品扩展：保留设计，不强制当前实施

## 为什么降级为 P2

当前 ACS Core 的核心任务是安全地让真实 Agent 通信。个人阅读状态、二进制附件、跨设备草稿、搜索与个人偏好主要改善通用即时通讯产品体验，不决定两端 Native 受信交流是否正确。旧包将这些列为完整客户端必交，导致 P0 核心正确性和 P1 客户端接口容易被非基础功能阻塞。此版本明确剥离交付门槛，并不否认它们的后续价值。

| 功能 | 优先级 | 保留要求 | 何时允许单独启动 |
|---|---|---|---|
| 个人 read frontier / 已读/未读 | P2 | 不得将 UI 已读当 Agent 消费；不得影响 ACS Inbox | 需要跨设备个人通知时 |
| 静音/归档/个人偏好 | P2 | 权限按 viewer 隔离，不能隐藏对端通信事实 | 有稳定客户端用户场景时 |
| Draft 多设备 CAS | P2 | 仅属于个人状态，不扩大项目和发信权限 | UI 已进入多设备输入时 |
| 全文检索 | P2 | 所有索引/搜索结果按实时权限过滤 | 历史增长到确有检索需求时 |
| 二进制附件服务 | P2 | digest/权限/大小/生命周期/跨主机可达性必须有证据 | 普通 Source/File 引用不再满足需求时 |
| 高级通知已看 | P2 | 系统故障 notice 独立于 Agent 消息，不能代答 | 客户端通知中心需要个人 seen 时 |
| 新增独立 Claude/Pi 等完整 Driver | 条件性 | 只在真实 Native 环境/安全准入合格时宣称 | 得到确切目标版本/环境时 |

## 已经实施的 P2 怎么办

不拆除、不迁移回旧状态、不回滚已合并成果、不删除生产数据表，也不将其从未来兼容合同中删除。对新安全边界受影响的现存 P2 功能，必须做相应回归；若当前功能没有生产/使用需求，Codex 可以停止继续扩展该项，而保留当前工作及记录。

## 旧包中的接口如何处理

旧 `contracts/openapi.yaml`、`models.schema.json` 含这些候选操作与 DTO。它们作为未来详细定义可使用，但不能让 P1 的 meta/服务声称已实现尚未开发的 P2。P2 的 endpoint/测试只在本版 `contracts/api-scope.json`、`contracts/scenario-scope.json` 与 `contracts/ui-scope.json` 中作为 `P2_optional` 保留。

## 不得为了减量删掉安全契约

即使 P2 未启用，普通消息中的既有 Source/Artifact 引用仍必须遵守权限和跨机器路径约束；如果二进制附件服务已存在，它也必须保留 digest、隔离、SSRF 防护和数据清理一致性。`R-026` 的 P2 部分并不降低所有资源访问的 P0 权限边界。
