# 14｜连续实施计划

| 工作包 | 用户可见成果 | 主要修改面 |
|---|---|---|
| WP00 | 可以从当前源码直接开始 | 当前工作树/来源/依赖和路径记录 |
| WP01 | 完整原生工作台运行 | 派生应用、现有构建与工作区/Chat，不重新设计UI |
| WP02 | 真正叫Porpita的应用 | 品牌配置、安装、CLI、数据目录、外部服务 |
| WP03 | UI完成Core连接和Agent接入 | onboarding/设置、托管依赖、可信MCP/Receiver配置 |
| WP04 | Agent真的收到和回复消息 | 现有ACS Receiver + 原生Host handover |
| WP05 | 原有协作行为均经ACS | send/ask/reply/check/group/report/wake/CLI |
| WP06 | 通信和P2功能可自然使用 | 现有组件、SDK/stores、source跳转、附件 |
| WP07 | 实际远端与重开可持续使用 | 远端receiver/host、恢复和数据导入 |
| WP08 | 可以安装和分发的产物 | electron-builder/Core依赖/版本/运行说明 |
| WP09 | 完整客户端真实验收 | 必须用户路径、真实模型/工具/安装版证据 |

按依赖执行；构建/品牌和服务接线可在互不覆盖的工作树并行，但每个负责人都以同一产品出口为目标。不要把“P0合格”“SDK通过”“界面能打开”作为完成并停止。

每个WP均要求实际代码或运行成果，不设单独的研究型前置阶段。完整任务在 `tasks/` 与机器可读 `contracts/work-packages.json`；可被Codex直接拆到当前源码，不要求用户补充上一轮进度。

每项新增复杂实现先问：现有Core/Host已经提供了吗？是正常功能缺口还是假想防御？能否通过更薄适配完成？这应当是日常代码判断，不是新的审批流程。
