# 13｜以真实用户功能为对象的验收

## 原则

验收回答“用户/Agent 是否真正完成了预定操作”。必要逻辑审查 + 核心实验通过即可接受相应支持范围，不要求证明所有理论异常。继承 Orca 工程时，验证改造后的接线，不重新审判全部上游实现。

包级检查不计产品验收；接口、fixtures、Host doubles 可用于开发，不能取代最终真实接入。所有 required 场景见 `contracts/acceptance-scenarios.json`。

## 最小充分证据

同一候选安装包的标识；每个真实场景的步骤/结果；能够看到主界面与过程的截图或短录屏；必要的 message/input/turn 引用和经过脱敏的日志即可。不创建新的大型证据数据库、不为每个字段录几十次失败窗口。

至少记录一次使用两个真实模型进程的 A→B→A 显式回复：用户在原生 Chat 提出实际开发请求，A 发起协作，B 使用真实工具，B 通过自身 ACS 身份回信，A 接到。不得由评测脚本代替模型发信、手工复制消息或直接插入数据库。

## 功能组

- 安装与首启：独立品牌、托管本地依赖、已有服务登录、无开发环境启动。
- 原生工作：窗口/工作区/Chat/终端/文件/Diff/审批与快捷键保留。
- 协作：自动可信配置、普通发信/回复、消息到实际 Native 输入、忙时输入不干扰当前工作、长期联系人。
- 客户端服务：实时历史/搜索/阅读/草稿/附件与来源跳转形成真实交互。
- 内核替换：普通、ask/reply/check、group、worker_done、远端和自动唤醒均按路径清单落实；无静默旧后端。
- 日常连续性：退出重开、一次断开恢复、一次身份/会话变化不造成错人和重复输入。

只有后两项的必要负例围绕直接受影响边界，不扩展为防御主线。保留的安全措施可以合并简化，但不能用测试删断言伪造正常功能。

## UI 比较而非新产品研究

在固定上游和候选中用相同窗口、主题、仓库和模型条件检查主要屏幕与操作，不追求微小像素零差异。确认没有新的强制技术表单、主导航组织树、重复 composer 或原生功能缺失。

本轮不要求给两种协作模型做统计排名。保留隔离上游安装作为后续对照即可；正式 Porpita 只使用 ACS。功能接通后可记录直接体验断点，用于后续讨论，不以比较研究阻塞交付。

## 完成状态

`PRODUCT_ACCEPTED` 必须：required 场景实际通过；核心 artifact 存在；两个源码与环境范围明确；必要外部依赖已真实接通；未测试平台准确列出。

`CANDIDATE_WITH_BLOCKERS` 用于已完成部分开发但欠凭据/目标 OS/安装运行的情况。可交付候选和明确剩余动作，不称产品完成。普通 native 功能仅支持某 Harness 时按上游范围，不因其它 Harness 不能做同一动作而整体失败。

`tools/verify_delivery.py` 仅验证记录/文件引用，不知道图像内容、模型是否真实或代码是否正确。最终签署必须依据真实执行和人工观察。
