# 05｜用户无需成为运维人员：安装与首次启动

## 两条完成的连接路径

默认提供“在此设备使用”和“连接已有服务”，复用上游 onboarding/设置组件。第一条是托管本地 ACS；第二条连接已部署的独立 ACS。两者在同一个正常 UI 中可诊断、断开、重连。

### 托管本地

Porpita 使用固定版本的 ACS wheel/SDK 和独立私有数据目录，配套运行 Python runtime 与 PostgreSQL。使用现有 ACS 启动、初始化和授权机制，不为方便改为 SQLite 或在 renderer 维护消息。依赖可以随安装包附带，也可以在首次启动经用户确认后按锁定清单下载；不要求用户执行 pip/uv/psql 或安装开发工具。

首代实际交付时，选择的打包策略必须有可运行产物、依赖来源/版本与许可记录，不能留“用户自行安装 Core”的隐藏步骤。没有可用下载/打包依赖时本地模式尚未完成；远端模式不自动替代本地必交。

托管实例是用户私有实例，不自动接管用户现有生产 ACS。复用既有 Core 安装时需明确用户选择。普通启动不修改原生产 schema；首次设置由受信 setup 执行已有显式 adoption，随后启动只验证。

### 已有服务

用户输入服务地址并走现有 OAuth/受信 Client 连接，不在 UI 输入 principal/Grant/Slot。读取 meta/profile，确认客户端 API/事件及已采用 schema。缺少必要 feature 时提供清楚的版本/启用提示，不让普通用户编辑服务配置文件。

远端服务生命周期不随客户端关闭而停止。用户凭据不写入消息正文、renderer localStorage 或公开日志。优先使用现有安全凭据存储，不开发新密钥平台。

## 启动流程

打开 Porpita → 原 onboarding 选择工作区/Agent → 选择本地或已有 ACS → 必要依赖安装/初始化 → 读取身份与服务能力 → 就绪。

界面只显示“协作服务准备中/已连接/需要处理”；错误详情可展开。没有 Core 时仍可使用原生单 Agent 工作，但不得展示跨 Agent 发送成功。

本地实例准备由宿主后台运行，UI 异步订阅进度。不要每打开一个窗口就启动一套 Python/PG；复用宿主既有单实例/daemon 模式。设置页提供服务版本、运行位置、连接状态、重新连接和日志入口，不暴露整个内部组织数据库。

## 退出、重开与升级

遵循上游窗口/托盘/后台运行设置：关闭窗口不等于删除会话；选择退出时正常终止本应用拥有的服务，保留消息/草稿/数据库。重新打开按原状态接续，不生成新身份代替旧用户。

升级先处理应用自身兼容；Core 需要 schema 变化时使用既有显式迁移/备份手段，不能 UI 启动时无提示做生产迁移。保留与原 Orca 并存能力：appId、userData、protocol、端口与服务名隔离。

## 日常用户操作

正常用户只需选择模型供应商并完成其原生登录；配置仓库；新增/切换 Agent；与其对话。Root/Route、可信注册、MCP 注入和 Session 关联由内部流程管理。首次开项目自动建立或选择内部 ACS namespace，不自动扫描并导入其他项目私信。

## 默认 feature 配置

在托管实例中启用已经实现的 communication client API、event stream、NativeLink 与本版使用的 P2 服务。具体字段以当前 `surface_config` 与 server settings 为准，禁止仅打开 HTTP 路由而遗漏存储 adoption。已有服务按实际 meta 功能展示，不靠客户端强行假定。

## 验收

在没有 Node/Python/PostgreSQL 开发环境的 Windows 用户目录内，安装、首次启动、本地服务准备、打开仓库与 Agent、关闭再开完整通过。远端模式也通过一次实际连接/注销重连；测试可以用隔离 ACS 实例，但不能是只返回固定 JSON 的 mock。
