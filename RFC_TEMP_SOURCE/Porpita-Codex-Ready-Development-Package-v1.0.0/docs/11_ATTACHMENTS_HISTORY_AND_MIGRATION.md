# 11｜附件、历史与首次采用

## 附件有两条独立使用路径

**原生 Chat composer 附件**继续由 Host/Harness 原生支持，不能为 ACS 迁移改坏。

**ACS 协作附件**使用已完成的 reservation/upload/finalize/download 与消息关联服务。用户通过协作消息入口发送，接收者能在 UI 打开/下载；为 Agent 使用时，Host 在目标实际执行机器把授权字节材料化为原生支持的 attachment/path。只传本机路径给远端 Agent 不算完成。

优先复用 Host 的文件/图片输入、缓存和 transfer 能力。没有通用原生文件对象的 Harness，可以给出宿主实际可读的临时/工作区材料路径并附明确语境；不要要求模型访问发送者的不可达路径。当前身份、文件来源与清理延用已有规则，不新建内容仓库。

首代至少让真实双 Agent 流程中的一个普通文本文件完整送达并被读取；有原生图片支持的主测试 Harness 也验证一张图片。其他类型按 native support 显示。可以明确显示“已分享，尚未交给 Agent”，不能用该状态永久替代首代要求的正常文件流。

## 现有 ACS 数据

本地新实例采用当前完整 schema；已有服务不自动升级/改生产配置。客户端连接前读 meta/profile，必要 feature 由 operator/托管 setup 启用。P2 已实现的历史、草稿、阅读与偏好保留，不因 UI 尚未接入而删除。

## Orca 既有用户数据

默认新 Porpita profile，原 Orca 继续可用。用户主动选择导入时，复制设置/工作区/原生会话索引，依照现有格式接续，不原地改写原安装。

旧 orchestration 消息在来源明确的只读历史中展示；不把不可证明的旧发件身份改成 ACS 作者，不重放旧待办，不把旧 task completion 当新消息。新 A2A 发送始终经过 ACS。

## 重新打开和退出

窗口关闭、应用退出、Core 连接中断要按实际发生区分。草稿与阅读状态保留；原生 Chat 已生成 transcript 和 ACS Message 都各自持续。只恢复各自系统已记录的原工作，不重复触发模型。以一次正常中断/重开测试证明用户体验，不强制建立全故障矩阵。

## 维护体验

提供用户可理解的备份/数据位置/诊断导出入口，沿用现有服务能力。卸载应用默认保留用户工作和通信数据，明确告知清理选项，不默认删项目仓库或原 Orca 数据。
