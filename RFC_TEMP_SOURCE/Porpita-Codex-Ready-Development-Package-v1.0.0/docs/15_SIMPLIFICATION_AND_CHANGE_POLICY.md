# 15｜功能优先与最小工程约束

用户已明确：不希望为了小概率问题不断增加防御校验、状态机与维护负担。本轮以可感知功能和使用体验计进度。

## 应做的减法

同一事实已由Core或Host可靠检查，上层重复包装没有收益时合并/删除；已有input queue、operation receipt、authorization和migration优先复用。不为Porpita再造一个通用通信框架、三套日志、全平台调和系统或新的安全测试平台。

对Orca已有明确源码依据的机制，读懂输入/输出和副作用边界，接入后通过必要场景即可采用。不要求再做一套证明实验才允许开发UI。只对集成改变的边界补测试。

## 最少不能失真的事实

作者是谁、目标是谁、消息是否已保存、Host是否已接纳、是否得到显式回复必须按事实呈现；不为跑通Demo冒名、错投或把未知当成功。现有明确数据访问权限继续使用；用户减少防御复杂度不等于授权泄露私人历史。

这几条是产品行为定义，不是要求更多校验层。实现上尽量在一个合适边界处理，内部受信调用复用结果。

## 不开展全面删防御重构

允许按本轮真实接线路径精简，不能反过来启动一次“删除全部防御代码”的大型工程。与本轮无关的成熟模块不动。历史CI问题按当前影响处理，不让罕见环境资格阻塞正常可运行产品。

性能问题以实际启动、输入、渲染、切换与协作成本判断。不要每条消息全量扫库、每个token同步Core、每个窗口多启PG进程；也不凭主观复杂度宣称性能更好。

## 变更记录

仅对真正改变用户体验、协议兼容、数据归属、部署要求的决定写简短ADR。普通函数重构不要求额外审批。保留现有测试的有价值断言，修不正确fixture而非删除失败结果。
