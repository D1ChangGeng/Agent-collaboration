# 07｜UI/UX 原生复用与最小扩展

## 不重新设计产品

继续使用上游主窗口、侧栏、Tabs/Panes、工作区切换、Native Chat、Composer、工具折叠、Diff、审批、终端、设置、通知和快捷键。颜色、间距、字体、密度、空态、加载态、图标与动效沿用现有 design tokens / primitives。

本轮不输出新的设计系统、不先做视觉探索、不把主侧栏换成 Project→Root→Route 的树。品牌替换只改变产品身份，不成为主题/配色重做的理由。

## 首代必要的 UI 增量

1. **连接入口**：原 onboarding 和 Settings 内加入协作服务设置与连接状态；不新开运维后台。
2. **Agent 关联**：复用 New Agent / 会话菜单，必要时显示“加入协作/连接联系人”及友好名称。
3. **协作信息入口**：优先复用右侧 drawer / 原有通知面板，显示可见联系人、消息及回复；可从原生 Chat header/menu 进入。主工作区仍是原生 Chat，而不是第二套全屏聊天软件。
4. **来源与跳转**：原生输入可显示轻量协作者来源标识；ACS 消息中有“查看执行”动作，跳转到实际 Native Session/turn。不要把 internal handle 直接显示为标题。
5. **现有 P2 交互**：在上述通信入口内复用原生文本/文件控件加入未读、搜索、草稿、附件、静音/归档。与原生 Chat 的草稿和搜索范围明确区分。

以上是允许的默认集成落点，不要求照搬某个不存在的组件名。以当前实际源码的复用点为准；只有无法复用才新增薄容器。

## 保持原生工作过程完整

Composer 仍支持上游提供的模型/权限选项、附件、斜杠命令、排队/steer、stop 和原生问题回答；工具/思考折叠、代码块、文件路径、Diff、子 Agent/后台任务保持原渲染。ACS 不能把这些内容平铺成普通通信消息，也不能自动把最终 assistant 输出当 reply_to。

“协作消息视图”与“Native 工作对话”不是同一个模型。可以在同一个 pane/drawer 之间关联，但来源、作者与阅读权限不能混淆。

## 状态文案

默认只呈现对用户有行动意义的状态：已发送/等待接收/正在处理原生输入/对方已回复/需要重新连接。技术事实不足时明确“尚未确认”，不要通过绿色已读暗示模型理解。

在详情中区分：Core 已保存、Host 已接纳、原生正在工作、对方显式回复、我个人已读。一般界面不用同时显示全部状态。

错误反馈必须附实际可执行动作：检查连接、打开目标会话、重试确定未发送的操作、查看原操作；不输出只有工程师理解的 epoch/fence 作为唯一解释。

## 视觉与交互验收

先记录固定上游基线的同平台真实主要页面：首次启动、工作区、Chat、工具/Diff、审批、终端、设置。Porpita 在相同窗口尺寸、主题和内容密度下比较，允许产品名/图标和批准的小扩展，不要求像素完全相同。

验收必须观察最终应用，不用设计稿或网页仿制品代替。中文输入法、键盘发送、复制、搜索、焦点、滚动与布局恢复至少走正常路径。优先沿用现有测试工具，新增场景仅围绕改动。

## 无品牌控制台化

默认首页不得堆砌服务拓扑、协议状态、签名结果、数据库表、Root/Route 计数。高级诊断可存在，但首屏服务于真实开发和协作。生物学隐喻只用于品牌叙述，不把“群落/个员/触手”强行映射为功能命名。
