# ACS v2.3.1 production acceptance

Both selected services run the published v2.3.1 candidate
`684f3066dae8cda63e380c03431b9f26f5d35a39`, tree
`d7e2a8ee203febe95dfb53bfcdd493c4f4c1284b`. PR #33 merged the implementation,
qualification and release metadata. Both exact candidate CI runs, release
preflight, archive/wheel source-byte comparisons and independent public download
of all seven initial assets passed.

The existing owner installation used the verified Bootstrap with its original
machine/account, Runtime-only, Harness, web and startup selections. All 1,037
source payload files verify. The receiving node's strictly installed wheel has
121 verified registered files. Only its proven owned idle ACS service was
stopped. The original Node key signed generation 9, and both trusted sides adopted
the actual process isolation proof. Identities, credentials, provider settings,
key hashes, ledger and Driver/Node Journal paths remain. All original records
and sealed packets remain. The existing uncertain delivery was retained without
reset or replay. Private backups remain on their original hosts.

The admitted read-only file connection now uses the verified active-release
entry and the original startup recovery lifecycle. Native local files stay on
the receiving host. Actual receiving-host MCP read six current owner management
documents, matched their hashes independently, reported current context and
refused writes and outside-root reads. The owned file daemon and its independent
loopback SSH tunnel were each stopped and recovered in one controlled test;
the new connection then read the same current files. This is a measured recovery
case, not a general latency guarantee. No Native service or host reboot was used
for this file-transport test.

The actual Client sent one new ordinary invoke+async message. The physical
Native Agent used its own ACS tools and message_only send to return one explicit
reply associated with that original. It reported ordinary identity, the actual
upper contact, five current instructions and one knowledge index from the owner,
two document hashes independently matched, its separate native local filesystem,
read-only remote operations and no management tools. Independent PostgreSQL
readback proves one request, one correct-author reply relationship, one Native
Attempt and signed generation 9. Native terminal output was not projected into a
reply and the new packets contain no task fields.

The refreshed real web Client reported Client/no Slot/no Native requirement and
zero collaborator self flags, including the legacy Root entry. Fresh Windows
connections report Client and current Root tools. Owned setup and knowledge
Skills were refreshed and digest-verified on all three selected client hosts;
unknown/custom payloads were not overwritten. The formal local checkout was
advanced while preserving the user's exact two README additions and all prior
stashes/untracked work. The remote formal source checkout was not substituted.

Root and Route Manager acceptance here uses actual MCP and PostgreSQL Sessions;
the physical Native post-upgrade scenario covers the ordinary receiving Agent.
One health read immediately after reply timed out; a bounded read-only retry
confirmed idle without any resend or reinvoke. Existing long-lived local MCP
connections retain their started version and were not forcibly closed. New
configured connections and the owned web transport use the activated release.
No production data cleanup, irreversible migration, or host/distribution reboot
was performed.
