# ACS 2.3.1 → Orca-owned Native sessions: source feasibility

Read-only source inquiry, 2026-11-06. ACS source root: `D:/Chatgpt/Agent-collaboration`. `pyproject.toml:7` is 2.3.1. The study verified branch/HEAD as `codex/core-cleanup` / `19d7881d49ee887315c54c5bc02e0cc424061376`; existing README modifications and untracked documentation/evidence were preserved. No ACS service, model, receiver, host or Orca runtime was started. This note establishes source feasibility, with runtime integration still to be tested if selected.

## Conclusion

Coexistence is source-feasible but not implemented or qualified for Orca. Keep Orca as the sole owner of its Codex/OpenCode process/session lifecycle; ACS can remain the authenticated Project/AgentSlot message authority and dispatch through a new trusted receiver adapter that asks Orca to deliver one admitted turn to an existing session. Do not start a second native receiver process or invoke the same turn from both ClientBridge and Core. Orca already has durable Run/Dispatch/inbox/thread/federation and provider-independent session lineage; those are not ACS-exclusive capabilities (upstream study baseline `9055eb9344dac1300311337cb1f0040d8094e3c2`, adoption-findings.md).

Current `COMMUNICATION.md:10-25,60-90` is the communication contract; `UPGRADE-CONTRACT.md:3-9` explicitly makes the old task/Gate mechanisms historical for this normal path. Do not introduce task result collection to obtain a natural reply.

## 1. Actual extension seams

- **Existing, typed native bridge:** `runtime/native_delivery.py:37-40` only accepts `CodexAppServerDriver` or `OpenCodeNativeDriver`; it also captures journal, kernel claim and identity (`:46-58,105-116`). A foreign Orca driver cannot simply be injected into this class. `runtime/drivers.py:36-51` is a thin invoke protocol, explicitly not native lifecycle conformance (`:41-42`), so its presence does not solve this.
- **Existing, factory seam:** `runtime/receiver_entry.py:24-33,55-88,149-158` loads a factory returning `DeploymentCallbacks(authorize_current,native_invoke,readiness,close,clock)`. Factory references are constrained to `runtime_deployment.<module>:<function>` and pinned by file/package/callable/path/installation hashes (`runtime/receiver_deployment.py:22-36,109-149`). This is an operator-installed Python extension, not an arbitrary model-supplied callback or URL.
- **Existing signed receiver transport:** `runtime/remote_endpoint.py:161-180,267-301` calls the bound callback only behind the ReceiverService. `runtime/receiver_models.py:57-89` defines signed admission identity; `:103-117` defines prepare/dispatch/readback bodies. This can be reused. It is not evidence that Orca implements an ACS HTTP receiver today.
- **Existing duck-typed lower seam:** `ReceiverNativeDeliveryBridge` accepts a `native_adapter` without an `isinstance` restriction, reconstructs the immutable prepared invocation, verifies lineage, then calls `prepare` / `invoke(on_dispatch=...)` (`runtime/receiver_delivery.py:80-149`). A new Orca adapter could implement this contract instead of weakening NativeDeliveryAdapter's type gate. Its correctness still needs integration evidence.

## 2. Existing-session adoption

There is more than spawn-only driver code: Codex `attach(operation,client,thread_id)` reads the actual thread/session and uses `shared_attached` (`runtime/codex_driver.py:771-784`); OpenCode attach requires a fresh authorized `LoopbackHttp`, matching cwd and actual session readback (`runtime/opencode_driver.py:773-788`). Both permit mutations of `shared_attached` only under native execution mode (`codex_driver.py:786-789`; `opencode_driver.py:790-795`). These are real low-level contracts, **not an implemented Orca binding**. Attaching directly while Orca still writes to the same session would preserve two controllers and bypass Orca's own queue/fences.

The shipped Codex factory constructs its own driver/supervisor and immediately spawns (`runtime_deployment/receiver_codex.py:238-268`); OpenCode constructs its own driver/adapter (`runtime_deployment/receiver_opencode.py:147-155`). `configure_team` accepts an already-admitted endpoint, not a native session identifier (`runtime/communication_management.py:98,128-134`), and initially returns no session claim (`:237-239`). A real provider must prepare/read back; absence is `provider_unavailable`, unverified binding is `receiver_unconfirmed` (`:26-65`). Native IDs cannot be fabricated from a configuration or replaced by an Orca durable ID without mapping and actual readback (`COMMUNICATION.md:60-90`).

Therefore source-only work can establish the possible seam and configuration shape; it cannot establish a **real** Orca endpoint/session binding without running an authorized real runtime. No existing setting turns an Orca session into an adopted ACS receiver automatically.

## 4. What an MCP message_only spike proves

**Can prove if actually exercised:** the particular harness can load ACS MCP; trusted caller maps to intended Slot; collaborators/inbox/history work; authenticated sender/recipient and reply_to are correct; explicit replies satisfy waits; reconnect can observe retained handles. `message_only` deliberately bypasses endpoint selection and records no requested native activation (`communication.py:403-407,443-447`; `COMMUNICATION.md:22-25`).

**Cannot prove:** Core→Orca activation, signed cross-host receiver transport, existing-session adoption, single-controller ownership, readiness, interrupt/cancel, crash/restart reconciliation, lost-ACK dedup, or Orca/native model consumption. Reading reports `model_consumption=unconfirmed` (`communication.py:350-352`). A successful exchange in one signed-in session also does not qualify another host/harness/version matrix. This inquiry ran no such spike and claims no runtime proof.

The first acceptance task should be one pre-existing Orca session, one ACS Slot and one request with the model's own associated reply. Then inject loss before/after the Orca mutation and replace/clear the session to show exactly one turn and correct fencing. These are proposed checks, not completed evidence. No HTTP endpoint design or production readiness is asserted here.
