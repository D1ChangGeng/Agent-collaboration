## 1. 产品定位与责任

ACS Client 服务于观察自己多个已注册项目的单个用户，汇集不同机器、不同 Harness 上的 AI 开发事实。用户能够查看项目结构、阅读协作进展、追踪 Agent 原生会话、阅读相关文件，并向 Client Agent 提问。

Client Agent 是用户级、可对话的只读助理。它能够跨项目查询获授权事实，解释结果，给出带来源引用的分析与建议。用户通过客户端管理自己的 Client 会话、草稿、消息队列、阅读状态和资源标签。

项目 Root、Route、Engineer、Reviewer 等 Agent 继续在各自外部 Harness 中工作。Core 保存权威协作事实、身份、授权与引用；ACS Client 的观察页面和 Client Agent 按授权读取。用户可以在 Client 中通过 Core 提交 Harness 的模型、模型服务商和推理强度配置修改，由独立配置权限和原生适配契约控制写入及结果核实。项目 Agent 的工作指令和模型调用仍遵循其外部 Harness 协作流程。

角色影响职责说明，不改变观察入口。所有已登记 Agent，包括 Root 与 Route 管理者，均可进入其会话目录，再读取明确绑定的原生会话与历史 trace。

## 2. 术语与对象关系

| 术语 | 产品含义与身份要求 |
|---|---|
| Project／项目 | 用户已注册的项目，使用稳定项目身份 |
| Route／开发方向 | 项目中的持久开发方向，拥有目标、知识与所属协作对象 |
| ACS Agent | 稳定责任身份，通过 AgentSlot 等明确绑定承载；与一次运行或一个会话区分 |
| 角色 | 管理、工程、评审等职责标签；不能单凭标签推导权限或实时执行状态 |
| Harness 会话 | Harness 原生 session/thread，拥有明确来源、原生标识与可验证绑定 |
| Client Agent 会话 | 用户与 Client Agent 的对话，由 Client Runtime 保存，与 Harness 会话分别呈现 |
| Task | 协作时间线中的工作对象，对应 Runtime 的 WorkItem |
| trace | 原生会话中按实际顺序呈现的输入、正文、公开推理与工具记录 |
| subject | 一条协作记录描述的业务对象，具有类型、身份与必要版本 |
| 资源引用 | 绑定授权范围、来源身份和精确版本的文档、文件、代码或会话引用 |

一个 ACS Agent 可以绑定多个 Harness 会话，并保留历史绑定。一次会话归属于哪个 Agent，应有绑定证据；一次调用或一条消息本身不能替代会话登记。

Client 会话的**项目归属**决定它在 sidebar 中的位置，以及此后新输入的默认项目上下文。对话中讨论或引用其他项目，不改变归属。项目上下文、Route 引用、附件与模型选择应在投递时形成可追溯的输入快照。

## 3. 应用框架与导航

### 3.1 主框架

首次使用先呈现左右分区的登录页：左侧是 ACS 标识、登录说明和“登录 ACS”主按钮，右半展示贴图或动态背景。点击后打开系统浏览器统一账号页完成登录／注册／验证；Client 切换为占满当前窗口内容区域的全屏状态视图，依次显示“等待浏览器登录”“正在验证账号”“正在准备工作空间”，准备完成后自动进入工作区。

浏览器统一账号页按“邮箱输入 → 密码输入 → 登录／注册操作 → 底部第三方登录区”排列。首批提供邮箱密码和“使用 GitHub 继续”；Google 后续接入时加入同一底部区域。登录与注册复用表单并使用各自明确操作。新账号验证邮箱和忘记密码复用邮箱验证码组件，提供验证码输入、验证、重发、修改邮箱及返回。注册验证后完成账号创建并返回 Client；找回验证后填写新密码与确认密码，保存后回到登录页并保留邮箱。验证码参数与旧会话失效策略继续细化。

Client 自动发现可授权接入的 Core、完成连接并读取已有配置。Core 安装流程负责准备可信的自动发现与连接条件；正常接入由系统完成。左右布局、素材渲染和全屏状态呈现由 Client 实现，账号登录与密码管理由配套账号服务承担，Core 提供真实身份、授权与接入结果。视觉风格及异常操作细节按区域继续确认，技术契约与 Core 缺口见 [用户流程与能力规划](USER-FLOWS.zh-CN.md)。

进入工作区后，应用由左侧 sidebar、主区顶部的全局页面标签、主内容和按页面类型提供的右阅读面板组成。首次准备完成后，按“Machine & Harness → Overview → 新聊天”进行认知引导。后续启动在账号和接入状态验证后默认进入新聊天；上次工作视角作为可选恢复。新聊天初态的主区显示居中的 composer；打开已有 Client 会话后，主区显示会话 trace，composer 固定于底部。

```text
┌─────────────────────┬──────────────────────────────────────────────┐
│ 新聊天               │ 全局页面标签：页面、会话、草稿                  │
│ Overview            ├──────────────────────────┬───────────────────┤
│ Machine & Harness   │                          │ 右阅读面板         │
├─────────────────────┤ 主内容                   │ 按页面类型组织     │
│ 项目会话目录         │                          │ 目录 / 资源标签    │
│                     │ 新聊天或 Client 会话     │                   │
│ 最近                │ 提供 composer            │                   │
└─────────────────────┴──────────────────────────┴───────────────────┘
```

右阅读面板的外层打开／关闭与内部目录的展开／收起是独立状态。面板关闭后，所属页面的资源标签、选择和阅读位置仍应保留。

### 3.2 页面路径

```mermaid
flowchart LR
    O[Overview 项目列表] --> P[ProjectOverview]
    P --> R[RouteOverview]
    P --> A[Agent 会话目录]
    R --> A
    A --> S[Agent View：指定原生会话]
    S --> C[子代理原生会话]
```

ProjectOverview 的主体顶部提供项目级 Root 和其他项目级 Agent 条目，下方为 Route 容器。任意 Agent 预览均可直接进入该 Agent 的会话目录。Route 的“查看”和底部 More 进入 RouteOverview。

返回操作恢复实际来源页面、筛选与滚动位置。通过明确引用导航时，先定位被引用的对象、记录或文件版本；普通标签切换恢复该标签此前的阅读状态。

### 3.3 全局页面标签

每个已打开的页面对象占一个全局 tab，包括 Machine & Harness、Overview、ProjectOverview、RouteOverview、Agent 会话目录、指定原生会话、Client 会话和新聊天草稿。全局目录类页面按当前账号与 Core 查看范围保存身份和状态。

页面身份使用“视图类型 + 稳定对象身份”。原生会话还须包含足以区分来源的 Harness 会话身份；草稿使用独立草稿身份。重复访问同一页面激活已有 tab，避免同一对象出现多个状态分叉的副本。

标签栏保持单行，超出宽度时横向滚动。各 tab 独立保存筛选、选中项、滚动锚点、面板状态、资源标签和与该页面关联的草稿状态。

关闭 tab 仅关闭视图。Client 会话、已持久化草稿与队列、已打开文件的资源身份继续保留；项目执行和正在生成的 Client 回答分别遵循自身生命周期。

### 3.4 首次认知引导与日常启动

首次完成账号验证和自动准备后进入 Machine & Harness，随后进入 Overview，最后进入新聊天。三步分别帮助用户认识开发环境、项目和 Client Agent 的使用入口，复用相应常规页面。页面内推进、稍后处理、主动续接与进度保存按流程文档 §2.48 已确认规则实施。

```mermaid
flowchart LR
    M[Machine & Harness] --> O[Overview] --> N[新聊天]
```

后续普通启动默认显示新聊天。Client 保存旧页面、草稿、队列和阅读位置，用户需要时主动选择恢复上次工作视角。普通页面返回、标签切换和显式引用定位仍按原来的阅读恢复规则处理。默认新聊天的打开只创建未发送草稿视图，首次正式发送才创建会话。

引导激活时，环境页与 Overview 的主内容右下提供小控件，分别为“认识环境 · 1/3／查看项目 →”与“认识项目 · 2/3／进入新聊天 →”，均可“稍后”并停留当前页。沿第二步进入新聊天后收起控件，记录认知路径完成，实际配置和模型状态独立保留。主动导航或关闭引导页暂停，日常重开仍新聊天；未完成时从“新聊天”旁“⋯ → 继续首次引导”主动续接。进度按本机 Client 安装及账号保存，恢复目标另带工作区引用，新增对象或换连接不自动重走；草稿复用按其真实身份，跨设备政策另定。工作视角与草稿恢复菜单按流程文档 §2.49 已确认规则实施。

日常恢复在“新聊天”旁菜单提供“恢复上次工作视角”和“恢复草稿…”。启动空白保留独立的待恢复来源，恢复按稳定对象身份补齐视图并保留当前编辑／阅读状态；草稿浮层按实际修改时间列出当前未投递版本，预览最多 48 个可见字符，点选回到原草稿或会话 composer。恢复布局后按当前权限读取内容，身份不可见时使用安全提示；运行和队列按真实记录处理。版本冲突取舍及跨设备政策继续按所属流程细化。

Machine & Harness 为常驻的环境入口。主区直接展示机器矩形容器，每个容器内部呈现其 Harness 卡片，内容持续可见并随页面滚动。机器容器展示五个已确认字段：机器名称、本机／远程、系统、ACS 接入状态和更多入口。状态浮层、连接检查与共享名称菜单的本轮候选见流程文档 §2.11，当前 Core 能力核对与差额见 ED26／CG-05／CG-06。每张 Harness 卡片代表该机器上的一个独立接入环境，临时运行实例和原生会话放在环境详情中；同一环境被多个 Agent／项目使用时复用原卡。

“＋ 添加机器”作为独立小按钮常驻本页主内容视口右上角，随列表滚动持续可见；每台机器卡片区末尾设“＋ 接入 Harness”操作卡。机器可信接入并回读后，可携带稳定机器身份复用组件，接续 Harness 检测与添加，各步骤按真实结果呈现。主动接入流程完成返回时按稳定身份滚动到对应机器；添加了 Harness 则定位其卡片。普通刷新保留阅读位置。取消后续步骤或 Harness 接入失败时保留已完成机器登记，保存未成功的编辑保留输入值并显示红色文字提示。Client 负责按钮布局与滚动，Client Runtime 负责流程衔接与恢复，Core 提供身份、权限及各步骤结果回读，适配器执行真实检测与接入；实施缺口见流程文档 §2.17 与 CG-05／CG-06。

机器接入的完整正常路径以 2–3 次真实点击／确认为目标，从 Machine & Harness 的“＋ 添加机器”起计，持续到结果可见。复制或打开接入材料、跨设备执行、登录／授权、打开安装包及系统提示均计入实际操作；输入字段和跨设备搬运同时记录负担。统一接入卡、一次提交后连续执行与成功自动定位已确认，按流程文档 §2.18–2.22 的明确前置条件进行真实平台验收。

“＋ 添加机器”打开同一张接入卡，已发现／已保存目标与两种方式在卡内原位呈现；可信目标和推荐配置可预填，详细设置按需展开。用户查看目标 Core、机器及明确的安装／启动／读取影响后提交“连接”，系统在固定授权范围内连续检查、准备组件、启动、登记并验证实际通信。成功且用户仍停留在接入流程时自动返回并定位机器；用户已转去阅读其他页面时更新结果并提供定位入口，保留当前阅读位置。已授权的 Harness 发现可自动进行，后续配置按实际需要处理。

接入继续提供“在目标机器上接入”和“通过 SSH 接入”两种方式。授权候选保留真实名称、系统、本地／远程与状态；材料保留默认链接、按目标系统与终端生成的命令、复制反馈和稳定流程身份。字段与输入可预填时使用已核实的值，所需安装、启动与读取影响应在明确计划中呈现；既有有效授权可以复用。

SSH 方式首屏使用单个目标框，支持已保存目标、SSH 别名及 `user@host`，认证默认沿用本机 SSH 配置。“连接选项”按需展开用户名、端口和密钥选择；同卡展示接入 Core 与实际安装／启动／读取计划，点击“连接”提交后连续执行。首次信任或额外认证原位补充，真实操作计入完整预算；普通字段失败保留值与红提示，敏感凭据按当前认证状态取得。Client 实现表单，Client Runtime 管理 SSH 配置、凭据与主机信任，Core 负责机器接纳与真实结果回读。字段定义见流程文档 §2.23，运行阶段与必要输入按流程文档 §2.24 已确认规则实施，协议和平台适配待验证。

SSH 连接过程在原卡保留固定目标摘要、中间动态进度或必要输入、底部当前主操作。正常阶段自动推进，执行中可取消；首次信任展示完整公开指纹与实际保存范围，按需提供“信任并继续”；认证挑战对应的密码、口令或验证码使用“继续连接”。主机身份变化停止目标后续动作并显示核实入口，其他失败按真实原因处理。等待输入时保留次级取消，关闭保留真实等待状态；取消核实已执行结果并保留已安装或已登记事实。成功自动定位机器，额外确认计入实际操作数，具体服务要求见流程文档 §2.24。

目标网页按账号和流程权限展示接入目标、当前账号与用途。机器信息以关联组件证明为准，“已连接”以 Core 登记、所需权限和实际通信检查为准，网页与发起 Client 共用权威结果。尚未回应、确空、部分可用、授权问题与结果未知分别反馈；跨设备授权持续绑定原目标机器。

返回或关闭保留流程；取消核实材料与在途结果，已登记机器继续保留。材料过期、安装已完成而接入未完成等情况沿原流程恢复，失败编辑保留红提示。机器接入与后续 Harness 配置分别完成，实际发现与已接入状态分别呈现。Client 负责交互和定位，Client Runtime 负责连续编排，Core 和目标组件负责身份、授权及真实结果；CG-09 记录接入与恢复缺口。

Harness 发现结果在对应机器容器中原位补载；每个独立环境保持一张卡。未接入卡提供“接入”，打开既有大详情卡并带入机器、可信来源与读取范围；已接入卡沿用“查看详情”。信息与授权齐备时，主卡接入、详情确认接入两次主要操作后自动更新定位；必要认证或连接条件就地补充并按实际计数。扫描中、局部失败及确认空结果轻量提示，机器完成状态独立保留。Core 目录与模型投影沿用 CG-05／CG-07，独立观察来源接入由新增 CG-10 承担。

首次接入 Harness 且尚无可复用观察授权时，默认预填当前选定独立环境的全部会话与执行记录，由用户点击“确认接入”提交该范围的观察授权；用户可以更改。已有同主体、同来源的有效观察授权按实际范围复用，扩大时通过明确计划确认。环境范围以稳定来源和所属机器为边界，实际可读范围及覆盖仍需依据 Core 权限与原生能力核实；源记录缺失与尚未读取分别表达。接入区与范围摘要见流程文档 §2.26，具体选择器按原生能力验证。

Harness 大详情卡保留既有模型配置和环境资料，下方接入区显示自动带入的机器／独立来源、具体读取范围与“更改”，缺少地址、访问凭据或必要服务准备时就地补充。需要启动用于读取的服务时，在同一计划中说明机器、目录、归属和影响，由“确认接入”一次提交；取消与恢复按真实结果处理。提交后在原卡显示进度，真实验证完成后自动更新并定位，后台完成保留当前阅读位置。Client 提供接入区和条件输入，原生适配落实读取边界，Core CG-10 提供授权计划、来源登记及逐次读取回读。

“＋ 接入 Harness”在同卡带入所属机器，常用受支持 Harness 直接点选，选择后在授权范围自动查找来源。唯一且已核实的候选可预填，多个来源原位选择；“手动指定来源”仅展开适配器所需的程序位置、配置环境、服务地址或工作目录，按所选机器与真实连接上下文校验。命中已有来源时复用原卡和有效读取范围。确认软件缺失且支持安装，或用户主动选择安装时，在同卡展示计划，条件齐备后使用“安装并接入”；未知与离线按真实缺口处理。普通条件齐备时，入口、点选、确认三次完成提交，其他实际交互完整计数。来源目录归 CG-05，接纳与读取回读归 CG-10，第三方安装由目标适配器承担。

Harness 的“安装并接入”在同卡显示已带入机器、经兼容验证的推荐版本、程序位置、独立列出的配置／会话环境、读取范围及实际依赖／配置／服务准备影响，更多设置按需展开。一次提交后连续完成安装验证、观察服务准备、来源登记与真实读取，完成后更新定位原卡。必要登录和系统权限按实际需要补充并计数；既有来源身份及范围保持，共享程序的更新影响纳入计划。安装成功、观察接入及数据覆盖分别回报；失败保留编辑与红提示，取消先核实结果并保留既有数据。Client 呈现计划与进度，目标适配器执行安装及恢复，Core CG-10 关联来源、观察授权及阶段结果。

Harness 主卡片以名称、接入状态和模型配置为主体。点击“查看详情”出现居中的较大浮层卡片，上部展示模型配置，下部展示环境资料。详情包含默认模型、模型服务、来源支持的推理强度，以及所属机器、Harness 版本和配置来源；存在多份配置时使用“查看配置”选择读取范围，刷新后按真实来源更新。关闭后回到原机器容器和阅读位置。

用户可通过 Client → Core 编辑当前接入环境的默认模型配置，首批字段为模型服务商、模型和推理强度，按该顺序联动。服务商变化后重查所属模型，模型变化后重查可调强度；选择过程保留在草稿中，保存时统一校验组合并回读结果，展示实际影响范围。保存未成功的字段或关联组合保留编辑值，并显示就近红提示，按第 16.3 节的统一规则处理。服务商选择与新增服务／凭据采用对应的独立流程。配置读取见 CG-07，受限写入及分项结果见 CG-08；生效说明和具体恢复时序继续细化。引导前进控件、中途退出及继续方式、完成标记的本机保存范围按流程文档 §2.48 已确认规则实施；引导进度、实际配置状态和后台执行状态分别保存。

## 4. Sidebar 与状态保存

### 4.1 目录结构

sidebar 顶部固定区依次放“新聊天”、Overview、Machine & Harness；三个入口随独立滚动区保持固定。下方滚动区域先放项目目录，再放“最近”。Overview 承担项目总览入口，Machine & Harness 承担机器与 Harness 环境入口。

每个项目名称是 Client 会话目录容器，点击名称或箭头展开／收起。展开后默认展示前 5 个归属于该项目的 Client 会话；超过 5 个时显示“显示更多”，点击后在原位展开剩余会话，并提供“收起”恢复前 5 个。收起超出条目与折叠整个项目目录分别保存状态。

“最近”展示全部未绑定项目的 Client 会话，按最近活动排序，且不提供折叠。已经归属项目的会话只出现在对应项目目录中。

sidebar 的“显示更多”扩展当前目录；ProjectOverview Route 容器中的 More 导航到完整 Route 页面。两个控件的文案、可访问名称与交互反馈应清楚表达不同目的。

### 4.2 展开与阅读状态

内部目录与 Context 组件首次出现时默认展开。用户主动收起后，刷新与普通返回保留该选择。目录状态按所属页面与组件范围保存，不能由另一个页面的同名目录覆盖。

状态存储分别管理目录展开、选中资源、资源内滚动、外层面板开关和页面滚动；关闭外层面板不重置其内部状态。全局 tab 切换不清空输入正文、引用、项目或模型选择。

### 4.3 排序

| 列表 | 排序依据 |
|---|---|
| Project、Route、ACS Agent | 显示名稳定排序；同名使用稳定 ID 打破平局 |
| Client 会话 | 最近正式消息时间；未投递的编辑不充当会话活动 |
| Harness 会话 | 有来源证据的原生更新时间；缺失时明确表示该时间未知 |
| 协作记录 | Core 记录时间降序，最新在上，向下加载更早记录；相同时间以稳定记录顺序打破平局 |

实时数据更新应保持当前阅读锚点。新内容提示与排序更新不能使正在阅读的条目突然离开视野。

## 5. Client Agent 对话

### 5.1 新聊天与 composer

新聊天初态是居中 composer；已有 Client 会话中，composer 位于 trace 底部。有内容的引用或附件显示为可移除标签，便于检查本次输入携带的材料。

composer 常驻以下控件：

- more：添加 ACS 引用、文件或图片。
- 项目选择：为首条消息确定项目上下文。
- 模型选择：选择后续待投递输入使用的模型。Client Agent 首版同时提供 ACS 托管模型和用户自带模型服务；入口、来源标签、模型选择及返回按流程文档 §2.44 已确认规则实施。
- 统一发送／停止按钮：由非空白正文和当前生成状态决定行为。

模型控件尚无选择时显示“选择模型”，点击展开锚定浮层；顶部为“ACS 托管／自带服务”。首次未选模型默认浏览 ACS 托管，已有选择时打开对应来源并高亮。自带服务按连接分组并提供“＋ 添加模型服务”，该入口打开居中卡片，字段与返回按流程文档 §2.45 已确认规则实施。浏览标签保留当前选择，选定可用模型才更新当前草稿并收起；关闭或配置返回保持草稿、项目、引用及列表位置。尚无可用模型的发送动作先进入选择流程，选完回原草稿由用户明确发送；模型目录、权益与生成结果按真实阶段呈现。

添加模型服务卡按所选适配显示服务、连接名称、认证和必要地址／协议，额外选项按需展开，主操作为“连接并保存”。认证、连接、保存和目录结果分别呈现；保存失败保留编辑与红提示，保存成功后返回自带服务并定位连接，目录失败保留连接及恢复入口。关闭／取消保留原草稿和实际已完成结果，账号回调及凭据绑定对应目标。模型目录状态与手动 ID 字段按流程文档 §2.46 已确认规则实施。连接内可区分目录正常／部分／确空／失败／不支持，按适配支持提供“＋ 添加模型”；卡片固定所属连接，模型 ID 必填、显示名称可选，保存后返回并定位条目，再由用户选入草稿。手动模型保留输入来源及验证状态，在已确认选择条件下可先使用；重复身份复用、刷新保留手动配置及实际证据。首次使用与可选验证生成按流程文档 §2.47 已确认规则实施。

正常发送沿原 composer；首次缺少必要数据／费用授权时，用局部确认卡展示模型、接收方、可核验焦点、声明查询范围及实际费用条件，确认后受理，已有有效授权按范围复用。模型条目“⋯ → 验证生成”打开独立测试卡，用户明确开始一次有界短文本请求；进度、真实结果、停止与未知恢复均按实际来源呈现，关闭返回原模型列表。生成验证绑定连接配置与请求范围，实际模型输入继续沿 §2.39 留证。

从项目相关页面或项目会话发起的新草稿继承该项目；从全局 Overview 或未绑定会话发起时默认未绑定。Route 页面发起的新聊天可携带该 Route 的明确引用。从 Agent View 发起分析对话时，继承所属项目，并把当前原生会话或选中的 trace 记录作为可见、可移除的引用带入草稿。

首发前可修改项目选择。首次正式发送时才创建 Client 会话并加入 sidebar；仅输入正文、添加附件或切换页面不会创建空会话。首发后项目选择呈现为项目标签，改变归属通过会话菜单完成。

对象菜单、trace 单元／选区菜单和文件阅读操作统一提供“询问 Client Agent”。每次明确发起新分析建立独立草稿和全局标签，原页面及已有草稿保持；同一草稿按身份复用，在已有 Client 会话补材料使用其 composer。项目选择承载默认项目上下文，其他对象及精确片段以可移除引用标签承载焦点，点击可检查来源、版本／范围、读取状态并回看原文。

首次正式消息受理后建立 Client 会话并加入 sidebar；模型未配置时草稿仍可编辑，经模型配置返回后由用户发送。范围引用和实际材料分别记录，回答的有效引用由实际读取记录解析，打开准确会话／unit／文件版本后可返回原回答及草稿／队列位置。

具体交互按[流程文档](USER-FLOWS.zh-CN.md) §2.37 实施。分析上下文以用户焦点、可核验定位背景与工具按需读取相结合，组装、读取工具和预算规则见 §2.38；具体运行输入记录见 §2.39。

### 5.2 统一按钮与停止

“有文字”以正文存在非空白字符判定。

| 正文 | 生成状态 | 按钮外观 | 操作 |
|---|---|---|---|
| 有文字 | 空闲 | 亮白 ↑ | 发送并开始新轮次 |
| 有文字 | 生成中 | 亮白 ↑ | 固定本次输入并加入队列 |
| 无文字 | 生成中 | ■ | 停止当前 Client 回答 |
| 无文字 | 空闲 | 灰色 ↑，禁用 | 无操作 |

仅有附件或 ACS 引用而无正文是否可发送，保留为待确认项；实现不能据此自行扩大发送判定。

生成中按 Esc 停止当前 Client 回答并保留草稿。菜单、弹层和输入法等局部交互优先处理 Esc；局部交互消费该按键时，不继续触发停止。停止快捷方式应通过可发现的界面说明呈现。

停止作用于 Client Agent 当前回答，不影响项目 Agent 的工作。已有草稿、排队消息和当前轮次历史分别保留。停止请求发出后，在运行服务确认结束前显示“停止中”，保留尚在运行的状态语义并暂停队列自动消费；服务确认后再进入已停止状态。

### 5.3 输入快照

普通发送或入队时，固定当时的正文、引用、附件、目标 Client 会话、项目上下文和模型。后续修改 composer 不追改已入队输入。

Client Runtime 应分别持久化草稿、队列和运行轮次，令跨页面、关闭视图与重新打开不会混淆它们的生命周期。trace 中实际投入模型的输入与尚未投递的队列条目应有清楚边界。

输入按受理版本保存，队列编辑或直接发送的显式变更形成可追溯版本，在合法投递边界锁定实际内容与模型。Runtime 分别保存提问请求、实际准备上下文和逐次资料读取；每次模型 API 请求记录其采用的精确材料片段、历史／派生来源、裁剪及调用状态。Runtime 已读与某次请求已提交分别可查，模型输入使用受权内容投影。

精确引用保持选定版本，动态范围在消费时读取并留证；权限及政策在实际准备／读取／提交时重新校验。请求结果未知时先核实原调用，保留原输入映射。缓存、原文和完整载荷保留沿 F18 处理。具体语义按[流程文档](USER-FLOWS.zh-CN.md) §2.39 实施，材料记录与下述队列规则衔接。

## 6. 消息队列与直接发送

### 6.1 队列展示和编辑

生成期间提交的普通消息默认 FIFO 入队，在 composer 上方展示。每条支持撤销、原位编辑、调序和直接发送。队列为空时隐藏整个队列区域，并释放其占用空间。

队列编辑使用条目自己的编辑状态，不覆盖 composer 中的另一份草稿。保存编辑后保持该条目的队列位置；用户主动调序才改变次序。

编辑中的条目不投递。它到达队首但仍未保存时，队列等待该编辑结束，界面应说明等待原因。编辑、撤销与投递须在原子边界上判断；模型已接收的输入进入历史后，不能再由队列操作改写。

### 6.2 自动消费

当前回答正常结束后，队列按顺序逐条启动新的轮次。每条使用其已固定的上下文和模型，不能继承消费瞬间 composer 的新选择。

当前回答停止或失败时，保留剩余队列，并暂停自动消费。用户可选择继续队列，也可对指定条目使用直接发送。相关操作须让用户理解将处理哪条输入以及使用哪个模型。

队列状态对用户以“排队中”和“等待下一步加入”为主要表达。条目实际投入模型后移入 trace；等待、编辑和暂停原因作为条目或队列的附加状态呈现。

### 6.3 直接发送的时序

直接发送把选中消息安排到当前回答的下一个合法 model step／API call 输入构建边界。已在途的 API 调用继续完成；到达输入构建边界时，选中消息加入当前上下文。

如果当前回答在该操作处理期间已经结束，选中消息接续为新轮次。操作时必须明确并固定当前生成所用的模型；即使时序使其成为新轮次，也仍使用这个已明确的模型。

直接发送不改变其余普通队列条目的相对顺序。被选中消息保留自身正文、引用、目标会话与项目上下文，模型使用本次直接发送明确固定的值。

模型接受输入前，条目仍属于待投递状态，编辑／撤销遵循同一原子投递边界。实际接受后记录输入归属和使用模型，作为本轮历史的一部分。

### 6.4 队列实现约束

| 竞争场景 | 必须保持的行为 |
|---|---|
| 正常完成与入队同时发生 | 每条输入只启动一次，目标会话和模型快照保持一致 |
| 队首编辑与消费同时发生 | 未保存条目停留队列，不能投递半成品 |
| 撤销与投递同时发生 | 返回明确结果；已接收输入保持历史，不伪装为撤销成功 |
| 直接发送与当前轮次结束同时发生 | 按合法边界注入或新开轮次，模型选择保持一致 |
| 停止／失败与下一条消费相邻 | 保留未投递条目并暂停自动消费，显示实际已发生的边界 |
| 切换页面或关闭视图 | 后台轮次、队列与草稿继续按各自状态保存 |

## 7. Client 会话归属移动

移动归属改变 sidebar 位置，以及此后新建草稿的默认项目上下文。历史消息与引用继续保留原来源和原上下文。

移动时已经存在的草稿和队列条目保留各自上下文快照，并展示可见的上下文标记。会话当前归属不能覆盖尚未投递输入的原项目上下文；该标记的最终视觉样式另行细化。

会话中引用其他项目的文件或事实，只增加明确的引用关系，不自动触发归属移动。移动操作与资源授权分别处理，读取仍受目标资源的当前权限约束。

## 8. Overview：项目入口

Overview 的主区直接展示项目列表。每条项目由名称、少量 Core 真实结构计数和可选的最新 Agent 协作原文预览组成；点击项目进入 ProjectOverview。

目录识别后，同卡显示项目名称、协作管理目录及本次变更摘要。已有项目优先复用经核实名称和管理目录；新项目提供可编辑的名称建议及项目内推荐位置，提交前展示具体路径。已有目录迁移、已登记项目改名按明确更新计划处理，稳定身份保持。“查看变更”展开实际新建、增补、保留的文件和 Core 登记／来源关联，包含源码根 `.gitignore` 等实际影响；“接入项目”一次提交当前计划。执行前复核文件和权限，外部变化原位重新核实；失败保留编辑与红提示，关闭保留流程，取消依实际完成项处理有界恢复。具体计划见流程文档 §2.30，统一文件计划与最小登记合同由 CG-11 补齐。

从仓库地址接入在同卡显示机器、地址、父目录、可更改的最终项目目录与远端默认分支策略，指定分支放入更多选项；真实分支在连接后核实。目标缺失／确空可克隆，非空先识别后选择接入既有目录或更改位置。一次“克隆并接入”提交克隆位置及后续管理资料的明确条件与写入范围，克隆后以实际身份、布局和文件生成具体阶段计划，符合授权时连续推进；冲突或扩大范围在原卡展示差异并确认调整。使用所选机器的仓库凭据，必要认证原位补充；克隆、检出、管理资料、Core 登记与所选资料导出分别核实。关闭保留流程，失败保留输入、工作副本与用户改动，重试先读回原结果；前后台完成按项目接入导航规则处理。实现责任见流程文档 §2.32、CG-11。

计数仅展示有权威来源和明确定义的数据。协作 Agent 数、工作数、阻塞数是可采用的数据类型；固定指标与条件展示集合仍待确认。配置有效的 Agent 数不能解释为正在运行的 Agent 数。

### 8.1 协作原文预览规范

Overview 项目条目和 ProjectOverview Agent 条目共用以下规范：

1. 正文单行，最多 48 个可见字符，标点和空格计入。
2. 原文超过 48 个可见字符时，显示前 47 个加省略号“…”；按用户可见字符计数，避免切断组合字符。
3. 宽度不足可提前截断；保留完整原文，供完整记录阅读与引用。
4. 作者和时间不计入正文的 48 字限制，时间固定在行尾。
5. 时间使用 Core 记录时间，按用户时区显示为 `MM-DD HH:mm`。
6. 没有可用协作记录时，省略预览行，保留项目或 Agent 的正常入口。

预览对应真实协作记录；列表渲染与观察刷新不触发额外模型分析。

## 11. Agent 会话目录

### 11.1 行内容与来源

一个目录行对应一个明确的原生 Harness 会话。Agent 的当前和历史绑定应能追溯，不能用最近一次绑定覆盖旧会话入口。

| 字段 | 展示规则 |
|---|---|
| Harness | 显示该会话的真实 Harness 标识 |
| 主标题 | 优先采用与该会话可靠关联的工作 goal；长内容按行宽截断 |
| 标题回退 | 无唯一可用 goal 时采用明确的原生会话标题；仍缺失时显示“未命名” |
| 更新时间 | 使用有来源证据的原生会话更新时间 |
| 接入时间 | 仅有 Core 绑定时间时明确标“接入时间”，不能充当原生创建或活动时间 |
| 详情 | 可读机器、完整目标、原生标识、绑定信息与各类已知时间 |

Root 仅调用 MCP 不证明其 native session 已被识别；原生会话必须通过登记或发现建立可靠关系。尚未发现、无权限、读取不支持和确实没有会话应分别表达。

### 11.2 打开与历史

点击行打开或激活该精确原生会话的 Agent View，全局 tab 与阅读状态均按会话身份保存。一个稳定 Agent 的多个会话分别可达。

新会话或新的子代理会话出现时更新目录和提示，不抢占用户已选会话。历史绑定能否读取、保留多久，应有适配与存储证据。

会话目录从 Core 的获授权索引自动呈现当前与历史原生会话；目录排序、新内容提示及局部状态排布按流程文档 §2.34 的已确认规则实施。既有目录行、全局标签和精确会话身份规则保持适用。

### 11.3 自动归属与维护职责

项目侧 Root／Route／执行 Agent 在其授权内提供身份上下文与关系证据，Harness／Node 适配提供原生身份和实际读取依据，Core 核验后维护稳定归属、修订及历史。Client 直接读取关系和真实可读状态；Client Agent 继续保持只读分析。Core 的确定性维护与外部 Agent 的推理／执行遵循各自权限，页面读取本身不启动项目模型任务。

证据尚未就绪时，受权维护机制保存具体状态并按实际条件补齐，Client 保留其他可读内容。用户需要处理账号、授权或机器连接时，通过对应来源的配置入口恢复；归属维护由 Core 与项目侧机制承担。完整归属链及 Agent 历史索引属于 CG-12 待实施能力，已有 WorkItem 绑定受理与原生会话事实验证分别取证。

### 11.4 排序、更新与读取状态

当前与历史会话共用列表。首次建立列表时按可靠原生更新时间倒序，同时间按稳定身份排序；时间缺失的行在尾部保持稳定顺序，只有接入时间时明确标注其含义。同一原生会话按获核实的来源命名空间和稳定身份复用，独立会话分别成行。

首次取得会话以及空态收到首批结果时直接显示。阅读已有列表期间，已显示内容和状态原位更新，保持顺序与滚动；新的可靠会话通过既有刷新控件提示，用户主动刷新后更新排序。新增数量以刷新按钮角标呈现，数量未确定或内容更新使用小圆点；交互见流程文档 §2.35。切换标签、返回和恢复阅读视图保留原快照与位置。运行状态依有效原生证据呈现，任务完成另据其事实判定。

读取中、当前范围确空、身份待核实、来源离线、历史缺失、能力限制及失权分别呈现。局部失败保留仍获授权的其他记录和内容；缺少账号、授权或连接条件时定位对应来源配置。完整索引、分页及读取覆盖由 CG-12 与原生适配补齐，搜索入口和范围继续细化。

## 12. Agent View：原生 trace 阅读

### 12.1 基本呈现单位

Agent View 只读呈现选定原生会话的完整可见 trace。多轮历史由该会话覆盖；必要上下文按需查看，读取范围和缺口明确展示。

| Unit | 默认呈现 | 展开与来源要求 |
|---|---|---|
| Content | 正文直接呈现，不折叠 | 保留实际消息角色和来源；附件可嵌入正文 |
| Reasoning | 默认折叠 | 仅展示来源实际公开的 summary 或 text，并保留类别 |
| ToolCall | 调用摘要与状态 | 参数、结果、错误、diff 等按需展开；附件可嵌入结果 |

时间、用量等以 metadata 呈现。正文、推理、调用及结果保留实际顺序；原生 `user` role 不自动标为真人“你”，应依据来源表达实际角色。

工具结果可以单独到达或单独存在。只有关联可靠时才与调用合并；无法关联时保留结果的真实来源与独立位置。结果内部的文本属于该工具结果，不能误作独立 Content。

### 12.2 Action Unit 分组

Action Unit 是 trace 的显示容器，不新增执行事实。满足以下条件时，将连续 Reasoning 与 ToolCall 聚合为一个可展开组：

- 位于同轮两个独立 Content 之间，或位于最后一个 Content 之后的尾段。
- 连续 Reasoning 和 ToolCall 的合计数量达到 5 个。
- 同一调用的增量、状态和结果只计为一次调用。
- 分组不跨输入轮次、执行记录或 Agent 身份。

尾段即使尚无后续 Content 也可成组。出现下一段 Content 不证明前一工具已经结束，工具状态仍由实际记录决定。

历史分组默认折叠；折叠摘要必须保留失败、等待和记录缺口。实时达到阈值时不强行收起用户正在阅读的内容，用户主动展开的选择持续保留。

### 12.3 实时更新与阅读锚点

执行状态需要实时更新。原生文字和 Reasoning 在来源支持增量时流式呈现，也可采用批量刷新；读取界面不为整理观察内容额外触发模型分析。

对同一 unit 的快照校正应更新原 unit；delta 与快照归并需要可靠身份，避免重复正文或重复调用。缺少顺序或关联证据时保留缺口，不能补造执行关系。

用户上滚时暂停自动跟随，提供回到最新内容的入口。新记录和读取状态通过所属阅读控件表达，保持 trace 正文连续呈现及当前阅读位置；子会话和资源状态附于对应 Context 组件。读取异常／恢复中在标题旁显示状态图标，悬停或聚焦说明、点击展开局部状态与恢复浮层；离开底部时显示右下圆形 ↓，新内容加小圆点，点击回到最新并恢复实际可用的更新方式。具体交互见流程文档 §2.35。

首次打开的默认落点、显式引用定位、trace／Context 分区加载、断流回补及退出恢复按[流程文档](USER-FLOWS.zh-CN.md) §2.35 已确认规则实施；相关观察服务与来源验证差额登记于 CG-13。

### 12.4 进入与恢复

首次普通打开且无阅读状态时，定位到最近可读片段底部；再次进入恢复已有锚点、展开状态和 Context，显式引用优先定位精确对象。目标失效时保留引用并说明原因，其他阅读落点由用户选择。trace 与 Context 独立加载，获授权缓存可先呈现并标明来源／时间及覆盖。

向上按需补载历史时保持屏幕锚点。读取中断后保留仍可读部分，重连按实际游标或快照校正，稳定 unit 原位更新；缺口保留可查看标记及覆盖说明。读取连接和原生执行分别取证。切换或关闭阅读标签保存状态及观察生命周期，原生执行继续由 Harness／项目 Agent 管理；后台订阅规模、缓存时限另按实际能力确定。

## 13. 右阅读面板

### 13.1 Agent 会话面板

Agent View 的右面板常驻不可关闭的 Context 标签，首次打开时默认选中。Context 内的“文件”和“子代理”目录初态展开，可独立收起并保存选择。

每个文件版本占一个可关闭资源 tab；资源标签保持单行，超出宽度时横向滚动。重复打开同一版本复用已有 tab，另一版本使用可辨识的独立资源身份。关闭当前文件标签后选中相邻资源标签；最后一个文件标签关闭后回到 Context。关闭标签只关闭阅读视图，文件及其关联继续保留。

Context 汇总与当前原生会话明确关联的文件，以 Core 登记或传输引用为基础。文件用途可标为输入、参考、输出、验证；源码目录与成果文件的关联按已有资料和授权读取。

点击子代理条目，新开或激活全局原生会话 tab，复用同一种 trace 阅读视图，并保留父子关系。Harness 原生子代理关系与 ACS 稳定 Agent 身份关系分别保存，不能把任意 native 子代理直接等同于 ACS Agent。

子代理目录属于确认的产品功能。各 Harness 的可访问性、历史读取、实时更新和 retention 能力属于必须验证的适配项；不支持读取与确实零项使用不同状态。

关闭外层面板时，保留所属全局 tab 的 Context 展开状态、文件 tabs、选中项与滚动位置。

文件条目以名称为主体，同名时补必要路径／来源或短版本标识；有可靠依据时显示用途，完整来源与版本在条目信息中查看。点击精确版本在右侧资源 tab 独立加载，主 trace 保持位置；显式片段引用优先定位其版本内锚点。新版本以独立引用打开，当前阅读内容保持稳定，读取失败在对应资源内处理。

Context 每层列出当前原生会话的直接子代理，按可靠 goal／原生名称或可辨身份显示。点击子代理激活精确全局会话标签及它自己的 Context；通过父级路径返回精确父会话，恢复 trace 和文件阅读状态。可靠身份已知但内容不可读时保留实际缺口，只有委派调用时按其实际 ToolCall 记录呈现。两组分别处理加载、确空、部分结果、能力与权限状态，新条目保持现有阅读。

具体规则见[流程文档](USER-FLOWS.zh-CN.md) §2.36。CG-12／CG-13 分别扩展原生父子索引和会话文件引用／观察读取，已有资料字节后端按其权限与版本合同复用。

### 13.2 Project／Route 面板结构

ProjectOverview 与 RouteOverview 的右面板共同承载开发进展与长期产品文档。二者读取同项目获授权的文档目录，开发进展则分别使用 Project 和 Route 范围。

面板包含常驻“目录”标签、可关闭的“开发进展”标签，以及可关闭的文档／文件资源 tabs。标签保持单行并支持横向滚动；关闭当前标签后选中相邻标签，资源内容与关联继续保留。首次进入该页面时预开并选中“开发进展”。

“目录”提供以下入口：

- 当前 Project 或 Route 的开发进展。
- Core 明确标记的产品文档。
- 已登记的 `docs` 文档。
- 已登记的项目与 Route 知识目录，例如 `.agents/knowledge`。
- 按需展开的“仓库与工作区”资料。

目录和文档保留真实来源路径、范围与版本。同一个文件从多个目录入口出现时，共用同一资源引用；在同一面板中复用相同版本的 tab。跨视图仍使用同一资源身份，各自保留阅读状态。

长期架构、目标和产品文档可以独立阅读；开发进展通过精确版本引用连接这些文档。时间线和文档目录均不能为便利阅读暗中改换到最新版本。

### 13.3 进展关闭与重开

用户手动关闭“开发进展”后，选中相邻标签；其余可关闭标签均已关闭时回到“目录”。数据更新和普通返回保持该关闭状态。用户通过目录入口或明确记录引用打开时，恢复对应 scope 的进展视图。

普通重开恢复筛选、滚动和条目展开状态；显式定位引用优先命中目标记录。新进展提示不抢焦点，也不重置现有阅读状态。

### 13.4 仓库与工作区资料

GitHub 链接、worktree、本地／远程仓库以及工作副本位置作为配套资料按需展开。各位置具有自己的来源和观测依据。

单条历史记录仅展示与该记录明确关联的来源。当前项目工作位置不能用于推断旧记录发生在哪个仓库或工作副本。

## 14. 开发进展时间线

### 14.1 范围与层级

Project 时间线以 Route 为最小开发记录单位，展示 Route Agent 的完成汇报以及明确的项目级报告。Route 时间线按所属 Task 的 Message 与响应形成协作链，并辅以 Route 报告。

记录的 subject 与 sender／recipient 分别保存。消息发给 Route Agent 时，仍可因其 subject 属于某 WorkItem 而呈现在 Task 协作链中。

消息、回执和响应是完整来源关联的一部分。原生回复不一定再次调用 `send_message`，投影应依据可靠关联收录实际响应，并保留其来源类型。

### 14.2 主文与原文

每条记录的主文采用 Agent 实际写入的原文，按记录类型确定主字段：

| 记录类型 | 主文字段的语义 |
|---|---|
| 消息与回复 | 实际发送的正文 |
| 进展或完成报告 | Agent 面向用户写出的报告正文 |
| 其他协作操作 | Agent 为该调用写出的说明 |

同一记录具有多个原文字段时，按类型选择 primary；其他字段标明用途后按需展开，并保留各自原文引用。时间线按原文呈现主文，保留 Agent 实际表达的内容与语义。

机器投递、调度和执行日志用于底层关联、恢复与检验，不作为开发进展主文或同级时间线条目。

### 14.3 单条记录结构

每条记录按三层布局：

1. 头部：消息使用“作者 → 接收者”；没有接收者的报告使用“作者 · 进展报告／完成汇报”，类型取自记录字段。时间位于右侧。
2. 中部：Agent 原文；长正文可在原位展开，具体折叠行数待定。
3. 底部：仅展示实际存在的 Route／Task、资料和来源关联，组成一行入口。

正文与卡片空白处不自动导航，支持阅读、选取和复制。时间可查看完整年月日与时区。第 8.1 节的 48 字限制只适用于外部预览，不适用于时间线正文。

### 14.4 关联入口行为

| 入口 | 行为 |
|---|---|
| 作者／收件人 | 进入相应 ACS Agent 的会话目录 |
| Route | 进入该 RouteOverview，并打开对应开发进展 |
| Task | 打开所属 Route 时间线并聚焦该 Task；筛选可移除 |
| 资料 N | 原位展开资料清单；选择具体资料后打开精确版本资源 tab |
| 来源 | 原位展开原文类型及有依据的源会话、代码、工作副本引用；展开内容限定为这些来源资料 |
| 精确源会话引用 | 进入已知原生会话并定位对应 trace unit |
| 记录定位链接 | 重开匹配 scope 的开发进展并定位该记录 |

仅知道作者时，作者入口进入会话目录，不能伪装为“源会话”并跳到其最近会话。找不到原版本或原 unit 时说明不可读或定位缺口，保留引用身份，不暗换其他对象。

### 14.5 时间线视图模型

时间线以 Project 或 Route 的稳定身份确定 scope；可选的 Task 聚焦条件缩小当前 Route 内的记录范围。读取模型提供分页游标、已覆盖范围和稳定记录顺序，界面保存筛选、滚动锚点、条目展开与标签开关状态。

单条记录包含稳定 ID、记录类型、subject 及其层级关系、作者、可选接收者、Core 记录时间、primary 原文及引用、可选回复关联，以及实际存在的资料和来源引用。回复通过明确的关联身份连接原消息；时间相邻本身不足以建立回复关系。

同一原始记录可按范围出现在不同视图中，并共用记录身份与原文来源。分页补载和实时重放按该身份归并，保留当前阅读锚点。

## 15. 数据与服务契约

### 15.1 权威、读取与投影

Core 保存项目协作的权威事实、身份、授权和引用。原生会话与文件以明确来源为事实依据，配合必要快照形成可重建的读取模型；Client Runtime 管理 Client 对话、草稿、队列和运行轮次。

UI 与 Client Agent 读取相同的事实范围、权限和数据缺口。AI 解释保留来源引用；分析结果不反写项目状态，也不能替代原文记录。

分析上下文由用户焦点、最小可核验定位背景和工具按需取得的证据组成。Core 提供身份、结构位置、已知关系及缺口，Client Runtime 按固定规则组装；Client Agent 在明示范围内使用定位、发现、读取、追踪关系四类观察能力逐步取证。

工具结果保留来源、版本、实际范围及坐标、覆盖／截断和可用续读入口。定位焦点的类型化输入、字段覆盖、历史版本和后续读取入口按流程文档 §2.40 已确认合同实施：可信范围由 Runtime／Core 固定，各字段及关系带实际证据与时点，描述与未处理状态按预算返回，现有引用浮层显示其实际结果。发现资料按流程文档 §2.41 已确认合同提供有界结构／字面查询、实际匹配依据及可读引用，查询覆盖与分页交付分别表达；Runtime 按当前授权与总预算编排。读取证据按流程文档 §2.42 已确认合同返回实际原文／版本／范围，分别表达来源保留与本次交付，并按版本及当前权限继续读取；追踪关系候选见 §2.43。Runtime 执行初始、单次返回、累计读取和回答预留预算，并按版本与当前授权复用材料；精确焦点优先，长内容以有界原文和继续读取入口提供。消息观察等读取操作固定观察参数，由 Core 再核验权限及业务副作用边界。

composer 的引用／项目浮层区分已带入、可查询范围和本轮已读取；实际模型工具查询沿用 ToolCall 呈现，确定性准备的读取记录注明 Runtime 发起方。规则见[流程文档](USER-FLOWS.zh-CN.md) §2.38，具体输入受理、准备记录与逐次模型材料映射见 §2.39。Core 的轻量描述及有界读取差额记录为 CG-14，配合 CG-03／CG-12／CG-13 实施。

来源、文件与会话各有单一事实来源。索引、缓存和时间线投影应能够从权威记录与必要快照重建，不能成为另一套独立修改的协作事实。

### 15.2 协作原文写入目标

协作工具的 `args.content` 与独立 `report_progress` 是需要落地的写入契约目标：

- 作者由认证身份绑定，时间由 Core 绑定。
- 语义命令的 Agent 说明与命令在同一事务中按幂等规则保存一次。
- `list`、`read`、`wait` 等读取操作不制造进展记录。
- 报告绑定 subject kind／id／revision，区分 `progress`、`completion`，并携带 refs。
- 报告记录表达进展或完成汇报，本身不直接改变业务对象状态。

现有 `send_message` 的 Work 绑定与 Scope 约束应继续遵循其正式契约；Route 汇报需要适合 Route 语义的记录合同。新增记录不能借展示需求绕过 scope 或身份要求。相关接口关系参见 [MCP workflow contract](../runtime/P2-MCP-WORKFLOW-CONTRACT.md)。

完成汇报、正式 lifecycle 转换和 acceptance 分别保留语义与证据。时间线上出现“完成”原文，不等于 Core 已接受相应 WorkItem。

### 15.3 最小读取数据要求

以下是产品所需字段语义，实际字段名由实现契约确定。

| 读取对象 | 必需身份与关键数据 |
|---|---|
| Project／Route | 稳定 ID、显示名、父级关系、授权范围；目标和文档引用在有明确来源时提供 |
| ACS Agent | 稳定身份、职责标签、明确所属关系、当前与历史会话绑定 |
| SessionIndex | 来源／Harness／原生 session ID、绑定出处、已知机器、goal 关联、各类时间与能力 |
| trace unit | 稳定 unit 身份、会话身份、实际顺序／轮次、类别、内容、状态、关联与覆盖缺口 |
| 子代理关系 | 父子原生会话身份、关系来源、可访问性、历史／实时／保留能力 |
| 协作记录 | 记录 ID、类型、subject、作者、可选收件人、Core 时间、primary 原文与其他原文字段引用、可选回复关联 |
| 文件／文档 | 授权 scope、来源路径、稳定资源身份、版本、用途、关联对象、读取能力 |
| 资料与来源关联 | 精确对象／版本、可靠的记录或 unit 定位、来源类型、关联证据 |
| Client 输入 | 会话或草稿身份、正文、附件／引用、项目上下文与模型快照、投递状态 |
| 阅读状态 | 页面身份、tab、面板与目录状态、筛选、锚点、显式定位目标 |

### 15.4 需要实施和验证的能力

实现工作包括 Agent SessionIndex、文件关联、文档索引、原生观察采集、开发进展投影，以及 Client Runtime 与持久队列。每项均应记录当前支持的 Harness、入口、权限、历史范围与真实运行证据。

原生会话发现、Root 会话绑定、子代理目录、history／live／retention、Reasoning 公开范围与文件版本读取需要逐个适配验证。产品入口可以表达能力缺口，不能把未验证支持渲染为可用功能。

观察页面与 Client Agent 使用受限读取权限和模型访问配置；用户的 Harness 三项配置修改使用独立写权限，Core 在实际写入边界重新校验目标与授权。项目、文件、会话、精确引用及配置目标分别落实权限检查，界面与服务共同执行边界。

## 16. 数据状态、引用与恢复

### 16.1 区分数据状态

| 状态 | 用户可见含义与行为 |
|---|---|
| 加载中 | 尚在读取，不能提前宣称没有记录 |
| 确空 | 在已说明范围内完成读取，结果确实为空 |
| 部分 | 已有内容可读，同时标出尚未覆盖或缺失的部分 |
| 断联 | 保留仍获授权的可读历史，显示 last sync，提示实时数据不可更新 |
| 不支持 | 当前适配或数据源不提供该类读取能力 |
| 不可读 | 对象有明确身份，但当前无法读取其内容或所需版本 |
| 权限失效 | 停止展示受限内容，并说明对应区域需要恢复授权 |

当前执行状态、内容覆盖情况和同步状态分别表示。例如可以同时存在“执行状态未知”“历史仅覆盖部分”和“已断联”；不能用一个笼统状态互相替代。

局部缺口只影响对应区域。子代理不可读不应使已有主 trace 消失；单份文件缺失不应使整条协作记录不可读。权限失效时，受限内容也不能以历史缓存名义继续展示。

### 16.2 精确引用与导航恢复

显式引用打开准确对象、scope 和版本。跨会话文件先定位其会话上下文；独立登记于 Project／Route 的资料在相应级别读取，范围依据引用而非猜测。

引用命中现有全局 tab 或资源 tab 时复用它，并执行指定定位。普通返回和标签切换恢复阅读状态；显式记录或 unit 定位优先于原滚动位置。

缺失版本、过期权限和不支持读取分别反馈。引用身份、来源路径和已知版本保持可辨识，便于用户理解缺口和恢复条件。

### 16.3 配置表单的统一保存反馈

一次保存尝试中，未成功的字段或关联组合保留编辑值，并显示就近的红色提示和简短文字原因。已核实成功的部分恢复正常样式，更新已保存基线；其余修改继续留在同一编辑表单中。

正常处理中显示保存状态；提交结果尚未明确时，用“尚未确认保存”等文案准确说明，继续查询原操作。字段有依赖时按 Core 的组合结果处理，重试须满足当前权限、版本与依赖条件。保存成功但尚未实际应用的情况，分别呈现保存结果和生效说明。

编辑草稿、已提交计划和当前配置分别维护。用户继续输入或重开表单时，保留获授权的草稿及相应提示；旧提交的成功回读不能覆盖后续新输入。敏感字段按既定安全存储和权限规则处理。
