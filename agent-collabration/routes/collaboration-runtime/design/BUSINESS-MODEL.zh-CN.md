# ACS 完整业务模型

状态：业务确认稿。本文先呈现对象、关系、流程、自由度和能力状态，
机制清理判断在用户确认业务模型后另行分析。

后续用户已确认业务价值与实际能力。授权、人工到期与机器使用限制的
清理范围见 [清理范围与业务影响](AUTHORIZATION-EXPIRY-CLEANUP.zh-CN.md)。
第 7 节的细分业务建议不自动视为已实施或逐项确认的变更。

源码核对基线：`e208a44f49927ead846623916ada828277401d00`。
当前机器的安装版本、私有集成和连接登记可能与源码基线不同；
“存在接口”与“当前机器完成真实流程”分别判断。

## 1. 产品目的与参与者

ACS 把不同机器、Harness 和会话中的 Agent 工作连接起来，让用户可以
组织项目、委派工作、沟通、等待结果，并在换会话和断线后继续协作。

| 参与者 | 业务责任 |
|---|---|
| 用户 | 提供目标、选择机器与项目、决定重要取舍和最终结果 |
| 本机或网页管理 Agent | 理解目标、查找上下文、拆分任务、选择协作者和下一步操作 |
| 执行或专业 Agent | 在具体 Harness 会话内编码、测试、分析、评审或完成其他请求 |
| ACS | 保存协作关系，提交确定性命令，投递消息，调用适配器，跟踪与恢复操作 |
| Harness | 提供模型会话、上下文、原生工具与执行环境 |
| 机器侧连接与执行服务 | 对接机器上的 Harness，报告实际状态，处理已有操作的运行恢复 |

任务如何拆、交给谁、结果是否满足目标，由用户或外部 Agent 决定。
ACS 的确定性操作与恢复围绕已经提交的请求进行。

## 2. 产品组成及入口

| 组成 | 用途 | 当前状态 |
|---|---|---|
| ACS Core / Runtime | 项目与协作记录、消息、执行适配、结果和恢复 | 已有实现，实际使用取决于部署与连接状态 |
| setup Skill | 安装、配置、修复，以及项目管理目录初始化或接入 | 已有实现，机器配置与项目接入分开 |
| 知识 Skills | 给外部 Agent 提供项目、职责、异步协作、源码和评审知识 | 已有文档和可安装 Skills |
| 本机 Codex / OpenCode | 用户与管理 Agent、执行 Agent 的交互入口 | 已有原生 Driver，能力依具体接入方式 |
| ChatGPT 网页入口 | 通过 MCP 读取项目、提交已支持的协作操作 | 已有私有 Tunnel 路径，目标机器执行另需真实可用入口 |
| ACS Client | 统一观察机器、项目、会话、trace，并提供分析与配置交互 | 已有产品设计；页面和完整服务能力需分别实现 |
| Client Agent | 对 Client 获得的项目和会话资料进行分析 | 设计中限定为只读分析，与项目执行 Agent 分开 |

Client 的账号、统一登录、模型服务连接、托管模型和自带模型服务属于
已讨论的产品设计。当前安装者的 Core 身份与 Client 商业账号不能直接
视为同一套已经运行的账户实现。

## 3. 对象与业务关系

### 3.1 项目与上下文

| 对象 | 业务含义 | 关系 |
|---|---|---|
| Project | 一个需要持续协作的项目 | 容纳管理资料、Route、任务、协作者和源码来源 |
| Management Root | 项目管理资料与稳定身份所在位置 | 对应 Project；保存指导、目录、决策和知识 |
| Route | 项目内一个持续工作方向 | 属于 Project；当前 WorkItem 创建入口要求指定 Route |
| SourceBinding | 项目资料或源码的来源关联 | Project 可有多个来源；Route 可关联多个来源 |
| Knowledge / Context | 指导、决策、背景和经验 | 由项目文件和知识系统维护，供会话按需加载 |
| ProjectContextPack | 给某次 Agent 会话使用的项目上下文 | 汇总身份、资料、Route、来源、活动工作与相关规则 |

一个项目可以在多台机器上有不同 checkout。机器路径、Git 分支和会话身份
分别记录。SourceBinding 表达具体来源与版本；业务项目身份跨路径和会话保留。

Route 是持续工作方向。Git 分支、worktree、机器和聊天会话是分别关联的
源码或执行环境。当前 Route 关联来源，但未定义它们之间永久一对一关系。

### 3.2 协作者与执行环境

| 对象 | 业务含义 | 关系 |
|---|---|---|
| AgentSlot | 可寻址的协作成员或责任位置 | 位于一个 Scope，可关联职责、工作和替换后的会话 |
| Role / Responsibility | 实现、评审、分析、协调、接受等职责 | 与组织层级分开；当前支持受限枚举与职责组合 |
| Team | 当前范围内的一组协作成员及设置 | 当前 configure_team 同时配置职责、权限、规则和预算 |
| Machine | 工作发生的机器 | 可有多个 Harness；同一机器可参与多个项目 |
| Harness | Codex、OpenCode 等执行产品或接入环境 | 产生原生会话，提供模型和工具 |
| Session | 一次具体聊天或执行上下文 | 可以替换；原生会话跨产品迁移不能视为已支持 |
| Endpoint | 消息与执行请求的接收入口 | Runtime 使用它连接逻辑协作者与实际接收程序 |
| Attempt | 某项工作的具体一次执行尝试 | 关联机器、会话和请求；恢复与替换保留历史关联 |

当前一个 WorkItem 在某个版本下有一个被记录的责任 Slot；多人参与可以
通过多项工作、消息、交接和评审组织。一个 Slot 可以关联多项工作和会话历史。
临时执行尝试与长期职责身份分别保存。

### 3.3 组织层级与职责

```text
Project
└─ Root Agent：项目协调
   └─ Route Agent：某个工作方向的协调
      ├─ 任务级 Agent：实现
      ├─ 任务级 Agent：评审
      ├─ 任务级 Agent：专业分析
      └─ 任务级 Agent：接受判断
```

Root Agent 是外部会话在某个项目承担的责任，不要求永久存在一个独立进程。
多个具备相应上下文和权限的会话可以管理同一项目；一个管理会话也可以
在不同项目中加载上下文并开展工作。

“Task Agent”是任务级 Agent 的待确认统称。当前组织声明支持 task 层级；
它还不是新的独立 Domain 实体。Slot、WorkItem 和 Session 的关系分别记录。

当前 Team 的主角色枚举为 root、route、engineer、reviewer、specialist、finalizer。
任意自定义角色尚未作为通用成员字段实现。角色描述与可执行操作目前通过
Profile、Grant 和 Policy 进一步关联。

### 3.4 工作、通信和成果

| 对象 | 业务含义 | 关系 |
|---|---|---|
| WorkItem | 一项持续跟踪的工作 | 当前属于 Route，包含目标、预期结果、约束、基线、证据要求和预算 |
| Message | 一次可跟踪的沟通或执行请求 | 当前公开发送接口必须关联 WorkItem，并指定同 Scope 的目标 Slot |
| Response | 对某个请求的回应或执行结果 | 通过稳定 handle 跟踪，可在后来读取 |
| Inbox / Outbox | 接收与投递中的持久消息记录 | 与某个临时聊天窗口分开，支持恢复和去重 |
| Handoff | 把已有工作的责任交给另一成员 | 关联工作版本、上下文、源码状态、未解决事项和确认结果 |
| Artifact | 文件、日志或结构化结果等成果 | 可由项目、任务、响应、证据和 Review 引用 |
| Evidence | 对成果、执行或观测事实的结构化记录 | 当前正式接受流程使用该记录和对应 bundle |
| Review | 对确定候选结果的评审 | 当前绑定具体工作、Reviewer、源码基线和证据集合 |
| AcceptedStateRevision | 一次正式接受的持久记录 | 与执行结果分别形成，保存对应候选和决定 |
| Activity | 协作变更的历史记录 | 用于查询项目发生了什么、由谁发起及关联对象 |

### 3.5 当前底层模型还包含的业务约束

| 对象 | 当前作用 |
|---|---|
| Tenant / Subject | 确定服务使用者和隔离范围 |
| Scope | 组织授权与协作状态的范围，Project 和 Route 都有相应关联 |
| Grant / Profile / Policy | 操作授权、工具可见性和附加规则 |
| Budget | 消息、待处理请求、重试等使用限制 |
| Lease / Protected Effect | 针对专用受保护资源记录占用和外部效果 |
| Incident / Human Bridge | 记录恢复异常及需要外部决定的处理请求 |

这些对象确实存在于当前模型。它们的 Core 必要性与默认适用范围，将在
业务确认后按清理规则评估。

## 4. 用户操作与流程

### 4.1 安装与机器接入

选择 Core 运行位置 → 准备依赖与身份 → 配置本机 Harness 连接 →
按选择配置网页入口 → 验证服务 → 保存配置。

机器安装和项目接入是不同生命周期。一次安装可管理多个项目。
新增执行机器需要准备真实机器侧接收与 Harness 环境，写入机器记录只是其中一步。
自动按需创建执行入口与完整接入流程尚未在现有通用工具中闭合。

### 4.2 项目接入与工作方向

定位已有项目 → 初始化或接入 Management Root → 保留项目身份与知识 →
登记项目及来源 → 加载项目上下文 → 创建或更新 Route。

现有 Runtime create_route 会建立 Route 登记和 Scope。
返回的 management_source_state 可以为 not_materialized；创建对应管理目录
和文件还需要 setup 或外部 Agent 的文件操作。

### 4.3 创建工作与执行

管理 Agent 理解目标 → 指定 Route → 创建 WorkItem →
选择协作成员和真实执行入口 → 发送执行请求 → 跟踪响应 → 判断下一步。

当前 create_work 要求目标、预期结果、约束、source_baseline、required_evidence、
budget 等字段。当前发送目标为该 WorkItem Scope 内的 Slot，且需要有效 Endpoint。
直接指定任意机器或原生聊天会话不是当前 send_message 的寻址模型。

执行 Agent 通过其 Harness 的原生工具完成编码、测试、研究或其他请求。
ACS 不自带通用 Shell 执行器；具体工具能力来自接入的 Harness。
非编码任务可以通过 Harness 执行，但当前工作记录仍采用上述正式字段结构。

### 4.4 消息、等待与通知

- message_only：提交沟通消息；不要求立即启动一次模型执行。
- invoke：提交让接收方开始处理的执行请求。
- 当前公开项目发送路径使用 queue_until_idle；忙碌时等待可用时机。
- async：消息提交后返回，后台投递、执行和响应跟踪继续。
- sync：等待目标响应或终态；显式 wait_timeout_seconds 可提前返回 pending。
- wait_for_response：对已有响应 handle 等待 any/all 条件，可选超时。
- completion notification：支持的会话接收唤醒信号，持久结果仍保存在 Inbox。
- check_inbox / read_message：后来进入的会话可以读取已有消息和结果。

通知是否主动唤醒 Agent 取决于 Harness 与客户端实际支持。Inbox 中有结果
不能等同于每种客户端都会自动开启下一轮模型思考。

Message 有效期、一次执行的限制和本次调用的等待时间分别表达。
调用者等待超时本身不会取消已经提交的工作。

### 4.5 交接与接力

选已有 WorkItem → 提供当前上下文、源码状态和未解决事项 →
指定接收成员 → 可要求确认 → 接收方接受或拒绝 → 继续工作。

当前具有 handoff_work、acknowledge_handoff 和 withdraw_handoff。
交接传递责任与资料；原生会话记忆和机器上的源码变化需要各自的实际接入或同步。
消息送达与 Git push/pull 的完成分别判断。

### 4.6 Review 与正式接受

完成执行并形成候选 → 记录成果与证据 → 明确选择 Reviewer →
提交评审意见 → 对源码与结果进行核对 → Finalizer 提交接受决定。

当前正式接受为 candidate → acceptance_ready → accepted。
Review、证据和相关绑定是当前接受流程的必要条件。
普通任务直接完成、按项目启用评审是新的 Core 契约方向，尚需改造实现。

### 4.7 取消、停止和异常恢复

- cancel_work：修改工作意图，记录取消及仍需跟踪的执行。
- stop_attempt：请求停止某次具体执行，读取适配器的实际确认。
- 断线重连：使用消息和操作身份恢复跟踪，避免重复提交。
- 换管理会话：重新加载项目并读取任务、响应及 Inbox。
- 执行状态不确定：先读取原操作，必要时通过 Incident/Human Bridge 请求外部决定。

取消工作、停止进程和回滚已经产生的外部变化是不同操作。
现有管理停止的保证限于适配器实际可控制的进程与会话。

### 4.8 源码与知识协作

外部 Agent 加载项目指导与知识 → 选择 SourceBinding →
读取文件、版本或差异 → 委派修改 → 由 Harness 处理修改与 Git 操作 →
读取新的来源状态并继续交接或 Review。

已实现普通项目源码读取。apply_patch、create_branch、commit_changes 和
push_changes 在目录中有可选合同定义，但不在当前 ProjectService 已实现集合中。
Harness 可以通过自己的工具进行源码操作；这与 ACS 提供源码写入接口分别判断。
当前项目 Source 绑定面向干净的固定基线；实时工作区视图属于拟改造方向。

### 4.9 多项目和 Client 使用

同一会话可以枚举可见项目，分别加载并汇总工作。操作仍明确对应某个项目。
跨项目或 Route 协调由外部 Agent 决策，现有普通消息不能任意跨 Scope 寻址。

Client 设计包含机器与 Harness 目录、项目概览、Agent 和会话目录、原生 trace、
只读分析对话以及模型配置。其已有产品确认内容与实现状态分别保存。
读取其他 Agent 的会话、分析资料和控制该 Agent 执行是不同能力。

## 5. 状态模型

| 状态维度 | 业务问题 | 当前表达 |
|---|---|---|
| 长期关系 | 哪些机器、项目、成员已经接入 | 项目、来源、Slot 和相应配置／登记 |
| 实时可用性 | 现在能否连接和执行 | Connection、Node、Endpoint、Harness 等观测与绑定 |
| 工作意图 | 这项工作要做什么、交给谁 | WorkItem 定义、revision 和交接记录 |
| 执行进度 | 是否开始、阻塞、失败或停止 | ready / running / blocked / failed / cancelled 及 Attempt 记录 |
| 执行结果 | 具体执行是否完成，返回了什么 | 原生执行回执、Response、Artifact |
| 消息状态 | 是否已提交、送达、执行确认、收到回复 | 投递阶段、响应跟踪、Inbox 消费状态 |
| 评审状态 | 候选是否被评审，意见是什么 | Review 请求、决定、findings 与未解决事项 |
| 正式接受 | 哪个成果被正式接受 | candidate / acceptance_ready / accepted 及接受记录 |

执行已经返回结果、工作被正式接受、成果已合入代码库或发布，是分别发生的事实。
当前 WorkItem 执行枚举没有一个通用 completed 值；完成事实还需结合执行回执与响应读取。

## 6. 当前自由度与明确边界

| 使用选择 | 当前模型的情况 |
|---|---|
| 同时管理多个项目 | 有项目枚举、加载与对应操作 |
| 一个方向包含多项工作 | 有 Route 与 WorkItem 关系 |
| 多个 Agent 并行协作 | 可用多项工作及多个执行入口组织，受实际适配与并发约束影响 |
| 一个 Agent 承担多种职责 | 有职责组合声明，受现有角色与权限枚举约束 |
| 自定义任意职责 | 通用 Team 字段尚未开放任意主角色 |
| 完成代码以外的工作 | 可委派给 Harness，当前仍沿用源码／证据导向的工作字段 |
| 不创建 Route 就创建普通任务 | 当前公开创建入口要求 Route |
| 不创建 WorkItem 就发送普通消息 | 当前公开发送入口要求 WorkItem |
| 发给任意机器、会话或其他 Scope 成员 | 当前按 WorkItem 范围内 Slot 寻址，需另行扩展模型 |
| 接入用户已经打开的任意会话并控制它 | 取决于原生 API 与 Driver；当前 attach 以只读接入为主，执行控制要求拥有实际控制通道 |
| 没有当前会话时自动创建后立即执行 | Driver 有启动能力，通用业务准备入口尚未闭合 |
| 普通任务完成后直接结束 | 执行可返回结果；正式 WorkItem 接受仍要求严格 Review 与证据路径 |
| 查看未提交工作区修改 | 当前项目 Source 固定基线读取，需扩展工作区视图 |
| 读取一切机器文件、执行任意 Shell | 普通 MCP 不提供这类通用接口；Harness 可执行范围取决于其环境 |
| 自动触发下一阶段或长期自主规划 | 外部 Agent 决策；已有命令可以恢复，Core 未提供通用自主规划服务 |
| 自动把源码从一台机器同步到另一台 | 消息交接与 Git 同步独立，需由外部工具完成实际同步 |

## 7. 供确认的目标业务选择

以下是业务选择，当前功能状态见上文，选择后再分析检查及实现拆分。

| 编号 | 待确认的业务关系或能力 | 建议起点 |
|---|---|---|
| B1 | ACS 可以承载的工作种类 | 编码、测试、研究、分析、文档、运维等 Harness 可执行的工作 |
| B2 | Project 是否是所有请求的前提 | 持续协作使用 Project；临时沟通和单次请求可独立发起，之后归入项目 |
| B3 | Route 是否是所有任务的前提 | Route 用于持续方向，可按需要组织任务 |
| B4 | WorkItem 是否是所有消息的前提 | 普通消息可独立发送；需持续跟踪的工作建立 WorkItem |
| B5 | Agent 组织与职责是否必须固定三级 | Root / Route / Task 作为常用组织方式，允许职责组合和灵活编组 |
| B6 | 请求目标可以是什么 | 指定协作者、机器上的 Harness，或适配器可接入的已有会话 |
| B7 | 执行环境是否必须预先存在 | 使用长期接入配置，按请求自动准备会话 |
| B8 | Review 与接受是否是普通任务必经流程 | 普通任务可完成；项目可以选择评审和接受要求 |
| B9 | 源码、版本、证据是否是所有工作的必需字段 | 根据工作类型选择资料与成果，普通工作可无 Git 基线 |
| B10 | Agent 之间能否跨方向或项目协调 | 外部 Agent 明确指定上下文，通过可解释的关系发起协调 |
| B11 | 接入外部会话的范围 | 按原生适配能力分别提供观察、消息、执行和停止 |
| B12 | Client 与项目 Agent 的责任 | Client 提供观察、配置与只读分析；项目 Agent 负责具体推理和执行 |

确定这些业务选择后，再逐项说明：需要保留什么状态、用户需提供什么信息、
哪些校验直接支持业务，以及哪些当前机制需要删除、合并、自动维护或改为可选策略。
